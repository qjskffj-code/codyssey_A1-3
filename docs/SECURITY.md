# Bound Mission 보안 및 API 키 사고 대응 절차

이 문서는 공개 데모에서 사용하는 Gemini API 키가 저장소, 화면 캡처, 로그 또는 제3자에게 노출됐거나 노출이 의심될 때 적용한다. **Git 커밋 삭제나 배포 롤백보다 키 무효화를 먼저 수행한다.** 이미 공개된 키는 파일에서 지워도 복사됐을 가능성이 있기 때문이다.

## 1. 현재 적용한 보호 조치

- 실제 키는 `.env.local`과 Vercel Environment Variables에서만 관리한다.
- `.env`, `.env.local`, `.venv/`는 `.gitignore`로 제외한다.
- 브라우저는 키를 직접 가지지 않고 같은 출처의 `POST /api/frame`만 호출한다.
- 서버 함수는 사용자 입력 본문과 API 키를 애플리케이션 로그에 기록하지 않는다.
- 공개 저장소와 화면 캡처에는 가상 데이터만 사용한다.
- 요청 본문 크기와 필드 길이를 제한하고 응답은 Pydantic 스키마로 검증한다.

## 2. 사고로 판단하는 조건

다음 중 하나라도 발생하면 실제 악용이 확인되지 않았더라도 유출 사고로 취급한다.

- 실제 키가 Git 커밋, Issue, Pull Request, 화면 캡처 또는 채팅에 나타남
- Vercel 로그나 다른 서비스의 로그에서 키 문자열이 확인됨
- Gemini 사용량이 예상과 다르게 증가하거나 알 수 없는 호출이 확인됨
- 키가 저장된 계정이나 장치에 제3자가 접근했을 가능성이 있음

## 3. 즉시 조치 — 0~15분

1. Google AI Studio 또는 연결된 Google Cloud 프로젝트에서 노출된 키를 **즉시 무효화**한다.
2. 필요하면 직전의 안전한 배포로 롤백하거나 AI 기능을 잠시 중지해 추가 호출을 차단한다.
3. 새 키를 발급하고 가능하면 Gemini API만 호출하도록 API 제한과 사용량 한도를 설정한다.
4. Vercel의 `GEMINI_API_KEY`를 새 값으로 교체하고 새 Production 배포를 실행한다.
5. 개발용 `.env.local`도 새 키로 교체하되 Git에는 추가하지 않는다.
6. 키를 발견한 시각, 노출 위치, 관련 커밋·배포를 키 문자열 없이 사고 기록에 남긴다.

> 배포를 이전 버전으로 롤백하는 것만으로는 이미 노출된 키가 무효화되지 않는다. 키 폐기가 항상 첫 조치다.

## 4. 조사와 영향 범위 확인 — 15~60분

- GitHub의 커밋·브랜치·Pull Request·Issue·Actions 산출물에서 노출 범위를 확인한다.
- Vercel의 배포 이력과 Function 로그에서 비정상 요청 시각·상태 코드·호출량을 확인한다.
- Gemini 또는 Google Cloud 사용량에서 평소와 다른 호출과 쿼터 소비를 확인한다.
- 공개 캡처, 공유 링크, 복제 저장소 또는 포크에 같은 값이 남았는지 확인한다.
- 로그 조사에는 시간·경로·상태 코드처럼 필요한 메타데이터만 사용하며 사용자 입력 본문이나 새 키를 복사하지 않는다.

## 5. 제거와 복구

1. 현재 파일, 문서, 캡처와 배포 설정에서 노출 값을 제거한다.
2. Git 기록에 키가 들어갔다면 이미 키를 폐기한 뒤 `git filter-repo` 또는 동등한 도구로 기록을 정리한다.
3. 공개 기록을 다시 쓰기 전 협업자에게 알리고, 정리 후 강제 푸시와 새 클론이 필요한 범위를 안내한다.
4. Vercel에 새 환경변수가 적용된 새 배포를 만들고 이전 취약 배포의 공개 접근 여부를 확인한다.
5. 배포 URL에서 정상 호출·빈 입력·오류 처리를 다시 테스트한다.
6. 비정상 사용이나 과금 가능성이 있으면 Google 지원 채널과 계정 관리자에게 보고한다.

## 6. 통지 기준

- 공개 저장소나 제출 자료에 노출됐다면 저장소 관리자와 평가 담당자에게 폐기·정리 완료 사실을 알린다.
- 다른 사람의 계정·데이터·비용에 영향이 있을 가능성이 있으면 해당 이해관계자에게 영향 범위와 대응 상태를 알린다.
- 이 데모는 사용자 입력을 별도로 저장하지 않으므로 키 사고와 사용자 데이터 사고를 구분한다. 조사에서 데이터 노출 정황이 발견되면 별도 개인정보 사고로 확대 대응한다.

## 7. 재발 방지와 감사 로깅

- 개발·Preview·Production 키를 분리하고 각 환경에 필요한 권한만 부여한다.
- API 제한, 호출 쿼터와 예산 알림을 설정하고 배포 전후 사용량을 확인한다.
- GitHub Secret Scanning과 Push Protection을 사용할 수 있으면 활성화한다.
- 커밋 전 `.env*`, 캡처, 로그와 변경 내역에 비밀값이 없는지 검사한다.
- CI에 비밀 패턴 검사를 추가하고 탐지 시 배포를 중단하도록 확장한다.
- Vercel 배포·환경변수 변경 이력과 Gemini 사용량을 감사 자료로 확인한다.
- 감사 로그에는 요청 시각, 결과 상태, 익명화된 운영 메타데이터만 남기고 API 키와 사용자 입력 본문은 남기지 않는다.
- 사고 후 원인, 탐지 경로, 대응 시간과 개선 항목을 기록하고 완료 여부를 재점검한다.

## 8. 복구 완료 기준

- 노출된 키가 무효화됨
- 새 키가 필요한 환경에만 등록됨
- 저장소 현재 버전과 공개 자료에서 비밀값이 제거됨
- 비정상 호출과 비용 영향이 확인됨
- Production의 정상·실패 시나리오가 다시 통과함
- 재발 방지 항목의 담당 작업과 완료 상태가 기록됨
