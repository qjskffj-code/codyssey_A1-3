# Bound Mission 서비스 기획서

## 1. 한 문장 정의

막연한 프로젝트를 **측정 가능한 끝점, 원하는 반응, 핵심 허들, 지켜야 할 경계, 오늘의 첫 행동**으로 바꾸는 프로젝트 프레이밍 도구.

## 2. 기획 배경

이전 프로젝트 Away를 만들며 “기능을 만들 수 있는가”와 “사람이 실제로 계속 쓰고 싶은가”는 서로 다른 문제라는 점을 발견했다. 완성도 높은 상용 할 일 앱의 구조와 사용 흐름을 관찰해 다음 행동 선택에 드는 부담을 줄이는 원리를 학습했고, 이를 독자적인 Bound 경험으로 재구성했다.

단순한 할 일 목록은 행동은 기록하지만 프로젝트가 어떤 상태에 도달해야 끝나는지 놓치기 쉽다. Bound Mission은 행동 목록과 끝점 프레임을 한 경험 안에 둔다.

## 3. 대상 사용자

- 아이디어는 있지만 성공 기준을 구체화하기 어려운 개인 프로젝트 수행자
- 해야 할 일은 많지만 우선순위와 다음 행동을 정하기 어려운 학습자
- 프로젝트를 시작하기 전에 범위와 장애물을 짧게 정리하고 싶은 사람

## 4. 사용자 문제와 해결 가설

| 사용자 문제 | 해결 가설 |
| --- | --- |
| 프로젝트의 완료 상태가 모호하다 | Metric Goal과 Desired Response를 함께 보여주면 수치와 경험을 균형 있게 정의할 수 있다 |
| 장애물보다 할 일부터 늘어난다 | Key Hurdle을 하나 고르면 가장 중요한 문제에 집중할 수 있다 |
| 범위가 계속 커진다 | Boundary를 최대 세 가지 가드레일로 제안하면 선택 기준이 선명해진다 |
| 다음 행동이 너무 크다 | 하루 안에 가능한 First Actions를 제안하면 시작 비용이 낮아진다 |

## 5. 정보 구조

### Thoughts

- 정리하기 전 생각과 선택적인 맥락을 빠르게 기록
- 현재 브라우저에 로컬 저장
- 선택한 생각을 AI Frame 입력으로 전달

### Today

- 오늘의 날짜와 완료율
- 일정 요약
- 다음 행동 목록
- 할 일 추가, 완료, 삭제
- 현재 브라우저 로컬 저장과 초기화

### Projects

- 샘플 프로젝트 카드와 진행률
- 선택한 프로젝트의 설명
- Metric Goal
- Desired Response
- Key Hurdle
- Boundaries

### AI Frame

- 입력: 프로젝트 이름, 만들고 싶은 변화, 현재 가장 막히는 점
- 출력: 프로젝트 제목, Metric Goals, Desired Responses, Key Hurdle, Boundaries, First Actions
- 결과는 구조화된 JSON 응답을 화면 카드로 변환

### About

- Away에서 Bound로 전환한 배경
- 상용 앱 분석을 통한 UX 학습 방법
- Bound에서 새롭게 더한 프레이밍 개념
- 학습 목적, 참고 관계, 개념 출처 고지

## 6. 핵심 사용자 흐름

```text
Thoughts에서 생각 기록 또는 AI Frame 진입
  → 필요하면 생각을 AI Frame으로 전달
  → 프로젝트 이름과 원하는 변화 입력
  → 선택적으로 현재 허들 입력
  → AI Frame 실행
  → 구조화된 끝점과 첫 행동 확인
  → 사용자가 판단해 자신의 계획으로 수정
```

보조 흐름은 Today에서 작은 행동을 추가하고 완료율 변화를 확인하는 것이다.

## 7. AI 기능 설계

### 입력

- 프로젝트 이름: 필수, 최대 80자
- 완료 시 만들고 싶은 변화: 필수, 최대 600자
- 현재 가장 막히는 점: 선택, 최대 400자

### 처리

- 서버의 Gemini API 호출
- Gemini Interactions REST API와 Pydantic JSON Schema를 사용한 Structured Outputs
- 사용자 입력은 프로젝트 맥락으로만 취급하도록 지시
- 짧은 프레이밍 작업에 맞춘 낮은 추론 수준과 출력 길이 제한
- 20초 서버 시간 제한
- 서버에서 사용자 본문 로그를 남기지 않음

### 출력

- 1~3개의 Metric Goals
- 1~3개의 Desired Responses
- 하나의 Key Hurdle
- 2~3개의 Boundaries
- 2~4개의 First Actions

### 실패 처리

| 상황 | 사용자 경험 |
| --- | --- |
| 필수 입력이 비어 있음 | 요청을 보내지 않고 필요한 입력을 안내 |
| 입력 길이 초과/잘못된 JSON | 입력 형식을 확인하도록 안내 |
| API 키 미설정 | AI 기능 설정이 필요하다고 안내 |
| 25초 이상 대기 | 브라우저에서 요청을 취소하고 재시도 안내 |
| API 연결 실패/시간 초과 | 원인을 짧게 설명하고 입력 내용 유지 |
| 요청 과다 | 잠시 후 재시도 안내 |
| 구조화 실패 | 결과를 만들지 못했음을 설명하고 재시도 안내 |

## 8. 반응형·접근성 원칙

- 데스크톱은 고정 사이드바, 모바일은 열고 닫는 메뉴 사용
- 700px 이하에서 카드와 AI 입력/결과를 한 열로 전환
- 모든 주요 기능은 `button`, `form`, `label` 등 의미 있는 HTML 요소 사용
- 아이콘 버튼에 접근 가능한 이름 제공
- 시스템의 동작 줄이기 설정을 존중
- 색만으로 완료 상태를 전달하지 않고 체크·텍스트 변화 병행

## 9. 데이터·보안 범위

- 공개 데모에는 가상 데이터만 포함
- Today 데이터는 브라우저 `localStorage`에 저장
- 계정, 데이터베이스, 실제 Bound 데이터와 연결하지 않음
- API 키는 프런트 코드에 포함하지 않고 Vercel 환경변수로 보관
- 요청 본문 크기와 각 필드 길이를 제한
- 공개 화면에 개인정보 입력 금지 안내

## 10. 성공 기준

- 사용자가 첫 방문 후 네 가지 핵심 화면을 이동할 수 있다.
- Today에서 항목을 추가·완료·삭제하고 새로고침 후에도 확인할 수 있다.
- AI Frame에 유효한 입력을 보내 구조화된 결과를 받는다.
- 빈 입력, 서버 오류, 시간 초과 중 하나 이상을 화면에서 명확히 확인할 수 있다.
- 데스크톱과 모바일에서 내용이 잘리거나 겹치지 않는다.
- 저장소에 API 키, 실제 사용자 데이터, 유료 원문이 포함되지 않는다.

## 11. 미션 이후 확장

- AI 결과를 사용자가 직접 편집하고 프로젝트 샘플로 저장
- 구조화 결과 내보내기
- 키보드 탐색과 스크린 리더 검증 강화
- 실제 Bound와는 계속 분리된 전시용 샘플 환경 유지
